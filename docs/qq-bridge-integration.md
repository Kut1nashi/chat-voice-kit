# 接到 QQ 桥接上（以 [qq-bridge](https://github.com/Derpyu520/qq-bridge) 为例）

> qq-bridge 是 MIT 授权的第三方项目。下面写的是**怎么在它（或任何同类桥接）里挂本套件**，
> 不是让你把它的源码整包再发一遍；要发 fork 就按其 MIT 条款保留原作者版权与许可声明。

## 1. 触发规则：什么时机回语音

纯文本聊天"按概率回语音"这条路，在**日语合成 + 中文对话**的组合下走不通：
合成引擎需要日语文本，而用户说的是中文，只有模型自己能给出日语。所以规则设计成：

| 条件 | 行为 |
| --- | --- |
| 对方刚发来**语音条** | 100% 用语音回（`lastIncomingWasVoice(key)` 判定最近一条非自己消息里是否有 `[语音]`） |
| 模型自己写出了 `日文原句||中文翻译` 分隔符 | 100% 用语音回 |
| 其它 | 纯文本，不要硬凑 |

已知设计缺口：判定只看"最新一条"消息。对方先发语音、又补了一句文字，规则就失效了。
要更稳就得改成"最近 N 条内出现过语音"。

## 2. 提示词：把格式写硬

模型不会自觉输出 `日文||中文`，得在**真正拼唤醒提示词的那个函数**里加一行硬要求
（qq-bridge 里是 `buildWakePromptV2`；一开始加在 console/admin 提醒里，实测不生效）：

```
【语音回复格式】回复语音时，第一行必须是 `日文原句||中文翻译`，两半都不能省。
```

配上 `lastIncomingWasVoice` 的判定，对"对方刚发语音"这一轮再追加一句
`【本轮硬性要求】对方刚发来语音条，必须按上面的格式输出`。

## 3. 代码挂点（qq-bridge 侧的改动清单）

| 位置 | 改什么 | 为什么 |
| --- | --- | --- |
| `config.json` → `socialV2.tools.sendVoice` | `true` | 工具开关 |
| `config.json` → `socialV2.voice` | `enabled: true`、`dir`、`maxSeconds`、`maxBytes`、**`maxPerMinute` / `maxPerHour`** | 语音总闸与限流 |
| `voiceCfg()` | 返回值里必须带上 `tts: { ...DEFAULT_TTS_CFG, ...(v.tts ?? {}) }` | **这个字段漏了的话 `vc.tts` 永远是 undefined，语音功能静默失效**（踩过） |
| 发送函数（`sendMessagesV2` 一类） | 加 `allowVoice` 参数；多气泡回复在"对方刚发语音"时也要合并成一次合成 | 否则两条气泡就退回文本 |
| `maybeReplyAsVoiceV2(key, text)` | 解析 `日文||中文` → 合成 → 发语音 → 再把中文那半当文本发一条 | 语音负责"听得见"，文本负责"看得懂" |
| 唤醒提示词构造 | 注入格式要求 | 见上 |

细节上要注意：**`text_split_method` 用 `cut2`**、**seed 固定**、
**发送前给首尾补 300ms 静音**——原因见 [`tuning-notes.md`](tuning-notes.md)。

## 4. 限流必须开

语音比文本贵得多（每次合成都要吃 GPU，还会有真实的"几条连发"），
配置里 `maxPerMinute` / `maxPerHour` 别设成 `0` 或很大的数，
按 `2 / 10` 起步，压力测试或批量对比时再临时放宽，**测完记得改回去**。

## 5. 排障顺序

1. `node src/tts-core.cjs --check` 看环境是否齐；
2. 手工 `node examples/say.cjs "テスト"` 能不能出 wav —— 能出说明合成侧没问题，问题在桥接；
3. 桥接日志里搜这几个关键字，它们各自对应一种静默失败：
   `语音总闸是关的`（`voice.enabled` 为 false）、
   `没有「日文||中文」分隔符，跳过语音改发文本`（提示词没生效）、
   `TTS 模块不可用`（`voiceCfg()` 没把 `tts` 字段透出来）。
4. 服务 9880 已经被别的实例占着也没关系：`VOICE_TTS_HOST/PORT` 指过去就能直接复用，
   本模块探活成功就不会再拉新进程。
